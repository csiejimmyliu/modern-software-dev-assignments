# Note of Reading Materials

## [Deep Dive into LLMs](https://www.youtube.com/watch?v=7xTGNNLPyMI)

[Andrej Karpathy](https://karpathy.ai/) explains how large language models (LLMs) power ChatGPT and similar products. He also drew a clear pipeline diagram in [Excalidraw](https://excalidraw.com/); you can [download it here](https://drive.google.com/file/d/1EZh5hNDzxMMy05uLhVryk061QYQGTxiN/view) on Google Drive.

Building a ChatGPT-style LLM typically involves three stages:
- **Pre-training**
- **Supervised Fine-tuning**
- **Reinforcement Learning**


### Pre-training
**Pre-training** fits a base model on a large text corpus so it learns to predict the **next token** (subwords, not whole words). At this stage, the model is not yet a chat assistant — it is essentially a **next-token generator**. It takes a sequence of tokens, outputs a probability distribution over the **next** token, samples from that distribution, appends the sampled token to the sequence, and repeats.

Here is the steps:

1. **Download and preprocess the internet:**
    This step involves crawling and cleaning large amounts of text data from the internet. [FineWeb](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1) is an example.

2. **Tokenization:**
    Tokenization converts raw text into a sequence of tokens, compressing language into a more compact representation. Frequently occurring patterns tend to become a single token — for example, "ing". Special tokens such as `<start>`, `<sep>`, and `<end>` are also manually defined for structural purposes.
    Here is a [visualization website](https://tiktokenizer.vercel.app/) to see tokenization in action.

3. **Neural network training:**
    The tokenized data is fed into a neural network (typically a Transformer), which is trained to predict the next token in a sequence. The model learns by minimizing the difference between its predictions and the actual tokens, updating its weights through backpropagation and gradient descent.
    
    The Transformer explaining videos by [3Blue1Brown](https://www.youtube.com/@3blue1brown):  
    [Transformers, the tech behind LLMs](https://www.youtube.com/watch?v=wjZofJX0v4M&t=42s)  
    [Attention in transformers](https://www.youtube.com/watch?v=eMlx5fFNoYc&t=61s)
    
    

4. **Inference:**
    Once trained, the model generates text autoregressively — it takes a sequence of tokens as input, outputs a probability distribution over the next token, samples from that distribution, appends the sampled token to the sequence, and repeats until a stop condition is met. (`<end>`)

**The "psychology" of a base model (pre-training).**
- **It dreams internet content:** When asked something it doesn't know, it generates a plausible-sounding answer based on the distribution of its training data, often confidently making things up (known as **hallucination**).
- **It can recite some training documents verbatim from memory (regurgitation):** For well-known articles like Wikipedia, simply prompting the model with the first few sentences may cause it to reproduce the entire passage word for word.
- **The parameters of the model are like a lossy zip file of the internet** — a large amount of world knowledge is compressed into the weights of the network, but only at a fuzzy, approximate level. It captures the general distribution of the data, not precise facts.


### Post-training: Supervised Fine-tuning

**Conversations**  
To fine-tune LLMs for dialogue, training data is formatted as multi-turn conversations using a special structure to distinguish speaker roles. For example:
```
Human: "What is 2+2?"
Assistant: "2+2 = 4"
Human: "What if it was * instead of +?"
Assistant: "2*2 = 4, same as 2+2!
```

This data was originally written entirely by humans. Today, it is more commonly generated by LLMs and then reviewed and corrected by humans, making the data collection process significantly more scalable.


**Solving Hallucination**  
**Hallucination:** When asked a question it doesn't know the answer to, the model will still
confidently generate a response — because at its core, it's just a
next-token prediction machine.

**How [Llama 3](https://arxiv.org/abs/2407.21783) addresses this (Knowledge Probing Pipeline):**

1. Extract a data snippet from the pre-training dataset
2. Prompt the model to generate a factual question based on that snippet
3. Sample multiple responses to that question
4. Score each response for **correctness** (using the snippet as reference)
   and **informativeness** — both judged by the model itself
5. If the model consistently gives confident but wrong answers,
   generate a **refusal** as training data (e.g. "I'm not sure about this")
6. Fine-tune on these refusals so it learns to say
   "I don't know" instead of hallucinating

> The core principle: post-training should not inject new knowledge.
> The model's outputs must stay consistent with what was seen during pre-training.


**Tool call**  
Similar to hallucination refusals, models are trained to recognize when they
shouldn't answer from memory alone — and instead call a tool to get reliable
information. Such as:

**Search**: when the question requires up-to-date or external knowledge  
**Code interpreter**: write and execute code, then use the actual output to answer — instead of guessing the result

This is also taught via SFT pairs, for example:  
- User: "What is the weather in Taipei?" →
  Assistant: `[call search tool]`
- User: "What is 1234 * 5678?" →
  Assistant: `[write and run code]`

And answer based on output.


**Concept of self**  
Models learn identity through explicit SFT pairs and system prompts, for example:
- User: "Who are you?" → Assistant: "I'm Claude, made by Anthropic."
- User: "Are you human?" → Assistant: "No, I'm an AI assistant."

Reinforcing a consistent persona.


**Models Need Tokens to Think**  
Why does CoT (Chain-of-Thought) work?  
Each token generation requires one full forward pass through the model.
If you ask the model to output only the final answer at once, it must compress all reasoning into a single inference — which is a lot to ask.

CoT works by spreading the problem across many inference steps,
allowing the model to produce intermediate results that feed into
the next token — effectively using its own output as a scratchpad.

**Things Models Struggle With**  
- **Counting**: e.g. "How many r's are in 'strawberry'?" — models tokenize words into subword chunks, so they never truly "see" individual characters.  
- **Spelling**: same reason — the model thinks in tokens, not letters.  
- **Numerical comparison**: e.g. "Which is bigger, 9.11 or 9.9?" — models often get this wrong because numbers are also tokenized inconsistently, and training data (e.g. the Bible, versioned documents) reinforces patterns like "9.11 > 9.9" in a chapter/verse context.

> The root cause: models don't process symbols the way humans do.
> They pattern-match over tokens, not characters or numbers.

### Post-training: Reinforcement Learning
Think of the three training stages like studying for an exam:

**Pre-training:** Reading textbooks extensively. The model absorbs a broad base of knowledge without any specific goal.  
**SFT (Supervised Fine-Tuning):** Solving practice problems that come with worked solutions. The model learns by imitating the demonstrated reasoning path.  
**RL (Reinforcement Learning):** Solving problems with no provided solution path.   The model explores freely and receives feedback only on whether the final answer is correct — learning to discover its own strategies through trial and error.

**How Reinforcement Learning Works**  
The goal of RL is to learn the best **solution path** — given a problem statement and a known answer, it searches for which sequence of tokens (reasoning pattern) leads there most effectively.

To do this, the model samples **multiple candidate solutions** for the same problem. The best-performing solutions are then selected as training pairs to update the model — gradually reinforcing the patterns that work.

> Unlike SFT, which imitates a fixed demonstration, RL discovers high-quality reasoning paths through exploration and feedback.


**Reward Model**  
A reward model is used to score candidate solutions when there is no clear right or wrong answer — such as "is this response helpful?" or "does this tone feel appropriate?". Since these qualities can't be verified by rules, a reward model is trained to simulate human preference and identify the best solution.  
When answers are programmatically verifiable (e.g. math, code execution), a rule-based reward signal is sufficient and no reward model is needed.


**RLHF (Reinforcement Learning from Human Feedback)**  
Instead of asking humans to produce the ideal answer as labeled data, RLHF only requires humans to **score or rank** candidate responses. This is significantly easier — evaluating a result is much more natural than constructing the perfect one from scratch.

This preference data is then used to **train a reward model**, which takes over the scoring process so human annotation doesn't need to happen at every training step.

**RLHF Upside:** It is easier to discriminate than to generate. Asking "which of these 5 poems is the best?" is far more approachable than asking someone to write the perfect poem from scratch. RLHF makes it practical to scale reward model training and align large models with human preferences.

**RLHF Downside:** The RL model will find ways to adversarially exploit the reward model — discovering inputs that score highly without being genuinely good. For example, generating ten dots and somehow fooling the reward model into rating it as an excellent poem. Since the reward model is only an approximation of human preference, it will always have blind spots to exploit.


## [AI prompt engineering: A deep dive](https://www.youtube.com/watch?v=T9aRN5JkmL8)

It's called engineering because it involves heavy trial and error, deliberate experimentation.

**What Makes a Good Prompt Engineer**
- Able to describe tasks and concepts with clarity.  
- Willing to iterate aggressively — sending hundreds of prompts to find the most precise instruction.
- Anticipates edge cases — thinking about how a prompt behaves when input is missing, malformed, or unexpected

**Practical Tips**  
- **Be explicit and thorough**  
Don't assume the model knows what you know. Treat it like a highly capable contractor with zero background context.  
A useful trick: speak your request out loud and transcribe it. Verbal descriptions tend to be more complete than deliberately typed prompts.
- **Iterate and observe**  
Read the model's output carefully, not just for correctness. Pay attention to tone and reasoning — they reveal how to improve the prompt. If the model makes a mistake, ask it why it went wrong and have it suggest how to revise the instruction to prevent it from happening again.
- **Give the model an out**
For edge cases, explicitly tell the model what to do when input is uncertain or malformed (e.g. output an "uncertain" label). This improves output quality and helps surface bad inputs early.
- **Guide reasoning with structure**  
Use "think step by step" or ask the model to reason before answering — this significantly improves performance on math and logic tasks. Use illustrative examples rather than overly specific ones to keep the model flexible and avoid rigid format mimicry.
- **Let the model help with prompt engineering**  
Have the model write prompts for you. Feed it a paper on prompting techniques and ask it to generate templates based on what it read. Similarly, use the model to generate test inputs or draft initial answers — refining from a draft is far easier than starting from scratch.
- **Respect the model's intelligence**  
Don't oversimplify. Give the model raw, complex material — dense papers, long documents — and it will generally handle it well without hand-holding.

Just as moving from assembly to high-level languages was a paradigm shift in how we express logic to machines, prompting is the next evolution — a new layer of abstraction where intent matters more than syntax.

**Zero-Shot Prompting:**  
Ask the model a question directly without any examples, relying solely on its pretrained knowledge to respond.

**K-Shot Prompting:**  
Provide K input/output examples in the prompt so the model learns the expected format and reasoning before answering.

**Chain-of-Thought Prompting:**  
Guide the model to reason step-by-step rather than jumping straight to an answer, useful for multi-step logic tasks.
- **Multi-Shot CoT:** Include examples that demonstrate reasoning steps, so the model learns to imitate the thought process.
- **Zero-Shot CoT:** No examples — just add a trigger phrase like "Let's think step by step" to elicit reasoning.

**Self-Consistency Prompting:**  
Sample the same question multiple times across different reasoning paths, then select the most frequent answer via majority vote to improve reliability and accuracy.

**Retrieval Augmented Generation (RAG):**  
Before generating a response, retrieve relevant documents from an external knowledge base and inject them into the prompt, allowing the model to answer based on up-to-date or private data while reducing hallucinations.

**Reflexion:**  
After receiving execution results or feedback, the model reflects on its mistakes and generates an improvement strategy before retrying — forming an "act → evaluate → reflect → act" loop.

### Best Practice
- Structure prompts clearly (separate role, task, and format). For example, use XML-style tags to organize inputs:
    ```
  Here are the logs:
  <log>
  LOG MESSAGE
  </log>
  and the stack trace:
  <error>
  STACK TRACE
  </error>
    ```
- Be explicit about language, tech stack, libraries, and constraints.
- Assume zero background context — provide complete details as if talking to someone unfamiliar with the topic.

## K-shot Prompting
This was the hardest part of the Week 1 assignment for me. The success rate remained quite low even after experimenting with different strategies.

1. **Words with similar length to "sutatsptth"**: The model struggled with these — too long and confusing to reverse reliably.
2. **Random few-shot examples**: Still struggled to internalize the core concept of reversing. 
3. **Classic simple words** (apple, abc, helloworld): Produced the best results. These words likely appear so frequently in training data that the model has an intuitive sense of their letter order — making reversal more reliable.

I ended up going with strategy 3, blending in a few more complex words to push the model's generalization.

## Chain-of-Thought
Beyond instructing the model to think step by step, I also explicitly guided each stage of the reasoning process in the prompt.
Output format requires extra attention — the model would occasionally arrive at the correct answer but fail to present it in the expected format.

## Tool Calling
Clearly specifying the tool call format and explaining each parameter in the prompt made a significant difference.
That said, having only one callable tool felt a bit too easy — the model simply returns the only available option regardless of intent.

A more robust test would define multiple tools and vary the user prompt to confirm the model genuinely selects based on the request.
```
tools: output_every_func_return_type, count_func
user prompt 1: give me the function return types
user prompt 2: count the number of functions
```
This way we can verify that tool selection is actually driven by the user's intent, not just a process of elimination.

## Self-consistency Prompting
The self-consistency mechanism in this assignment lives in the code itself, not in anything we control through the prompt.
It works by sampling the same prompt multiple times and taking the most frequent answer as the final output — essentially a majority vote over multiple runs.

## RAG (Retrieval-Augmented Generation)
**Data Flow**

1. **Load** — Read `api_docs.txt` into CORPUS as the knowledge base.
2. **Retrieve** — Context Provider selects relevant documents from CORPUS.
3. **Augment** — Combine the selected docs and the question into a single prompt.
4. **Generate** — Send the prompt to the LLM and obtain the generated code.
5. **Validate** — Check whether the output contains all required code snippets.

> **Note:** In this assignment, Retrieve simply hardcodes `corpus[0]`.
> In production, this step uses embedding-based vector search to surface the most relevant documents automatically.

## Reflexion
The LLM iteratively improves its own code based on failure feedback — rather than regenerating from scratch, it reflects on what went wrong and produces a targeted fix.

**Data Flow**

1. **Generate** — LLM writes the initial `is_valid_password()` implementation.
2. **Evaluate** — Run test cases and collect failure diagnostics.
3. **Reflect** — Feed the buggy code along with the failure messages back to the LLM.
4. **Regenerate** — LLM produces a corrected implementation.
5. **Validate** — Check whether the improved code passes all test cases.

> **Note:** In this assignment, Evaluate relies on hardcoded test cases.
> In production, this step could be delegated to an LLM judge for more flexible evaluation.
